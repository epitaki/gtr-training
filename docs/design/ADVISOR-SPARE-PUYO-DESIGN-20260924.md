# 余りぷよを構築中に減らすための設計

日付：2026-09-24。状態：設計案。**この文書の追加では推薦・採点・ツモ生成を変更しない。**

後続の実装・測定と採否は [実装記録](../records/ADVISOR-SPARE-PUYO-20260924.md) を参照。
以下は設計時点の分析と目標であり、全項目の実装完了を意味しない。

## 1. 目的と変更しない条件

GTR完成を優先したまま、用途のないぷよを積み続ける配置を減らす。
既存の「最後に余りを回収する」評価に加え、置く時点で組ぷよの両方の使い道を比較する。

- 現在・NEXT・NEXT2だけを使用する。見えていない将来のツモを補って成功扱いにしない。
- 今打てる本線5連鎖を、余り削減や伸ばしのために先送りしない。
- GTRの接続・消去順・合法性・発火口を保つ。用途未確定を理由に、完成に必要な配置まで禁止しない。
- 最小5連鎖土台の100点条件、Y字→座布団→L字の基本方針、4色供給・20手の測定条件を変更しない。
- 2・3列や右端への一律禁止、4段目以上の一律禁止、7連鎖を目指す加点は行わない。
- 残るぷよには次の連鎖や支持の用途もある。「発火後に残った＝すべて捨てぷよ」と断定しない。

## 2. 設計前に確認した事実

対象は[現行v2の保存済み500ゲーム](../../benchmarks/results/tail-cascade-20260924-v2-regression500.json)。
seed 20260904、通常4色、最大20手。今回は推薦を再実行せず、保存された手順を共通シミュレーターで再生・分析した。
参照レポートSHA-256：`8677ffb228b1384c51b4893c615c4a4d857c842337fc0cba572651ae8d64fd39`。

### 残りの分布

- 本線発火421ゲーム：残り合計3,251個、平均7.722個、中央値7個、最大20個。
- 8個以上残るゲーム205件（48.7%）、12個以上70件、2個以下25件。
- 右側3列に平均4.812個、2・3列に平均2.485個残る。
- 5連鎖以上の417ゲームに限っても平均7.647個、8個以上201件。3〜4連鎖の4件だけが平均を押し上げているのではない。

### 残ったぷよを、いつ置いたか

各手の軸・子に印を付け、共通シミュレーターの消去元位置で印を除き、残った印を列内順序を保って追跡した。
毎手の色付き盤面と保存盤面の一致、発火後の残数との一致を確認した。
これは後から原因を調べる診断であり、未来の結果を推薦の入力にするものではない。

| 置かれた時期 | 最後まで残った個数 | 割合 |
|---|---:|---:|
| 折り返し完成手まで | 1,004 | 30.9% |
| 折り返し完成後〜尾完成手まで | 506 | 15.6% |
| 尾完成後〜発火の前手まで | 1,501 | 46.2% |
| 尾が教材形として認定されなかったゲームの中間手 | 37 | 1.1% |

尾完成は教材尾の接続成立であり、5連鎖骨格全体の完成や発火色待ちと同じではない。
1,501個すべてが回避可能と証明したわけでもない。ただし、尾完成後の判断を最初に調べる根拠になる。
例：game19は尾完成7手目・発火17手目で10個残る。このうち9個は尾完成後から発火の前手までに置かれている。

## 3. 現行実装の弱点と仮説

| 確認できた実装上の事実 | 設計への示唆 |
|---|---|
| `PairPlacementUse`は軸・子だけを分類し、適用は折り返し完成後〜尾完成前に限る | 尾完成後と、既に盤面へ置かれた余剰の評価が必要。ただし既存の適用制限を外すだけにはしない |
| 骨格外のぷよには一律の余剰減点があり、未完成時には回収される余剰も用途不明も同様に扱われやすい | 支持・接続・条件付きの仕込み・用途未確定を分ける |
| `fit`で骨格を選んだ後に、選ばれた骨格だけにCURRENTの用途減点を計算する | 骨格ごとに用途も調べてから選ぶ。同じ盤面にある別の有効な構築案を見落とさない |
| 5連鎖発火の終端比較は手数と別消しを優先し、同等の発火候補の残数を比較しない | 発火を遅らせない同点比較から着手できる。自由形・骨格探索・最終候補ソートの全経路を揃える |
| 雪崩・鶴亀の追加点は、現在か見えている3組で骨格全体が完成する場合に限る | 本線完成前の仕込みを扱うには、実証済みの回収と条件付きの見込みを別の情報にする |

これらが余り全体の何個を生むかは、まだ因果分解していない。
[過去の2個用途評価](../records/ADVISOR-PAIR-USE-20260922.md)と[雪崩v1](../records/ADVISOR-TAIL-CASCADE-20260924.md)は、
広い適用や仮完成の加点で完成を遅らせた。単純に減点を増やす案は採らない。

## 4. 配置ごとの「用途」と「根拠」を分離する

一つの成立可能な骨格と、一つの合法な手順に対して、現在の2個と既存ぷよを評価する。
軸は骨格A、子は骨格Bという別案の都合のよい部分を合算しない。

| 用途 | 認定する根拠 |
|---|---|
| GTR土台・本線 | 適合する骨格の必要セル、または実際の本線消去への参加 |
| 支持・接続 | 同じ案で、必要セルの着地や後の落下接続を成立させる具体的な役割。真下にあるだけでは認定しない |
| 発火点伸ばし | 元のGTRへ戻る接続、必要色、支持順を検証できる形。最初は既存の左端限定形を使用 |
| 連鎖尾伸ばし | 雪崩・鶴亀など、本線の支持消去からつながることが分かる形 |
| 用途未確定 | 上記の根拠がない。ただし永久に使えないとは断定しない |
| 接続を妨げる | 同じ案で必要な色・着地点を塞ぐ、暴発する、発火口を失うことを物理検証したもの |

用途と別に、根拠の強さを持つ。

1. **現在成立**：今ある盤面で参加・接続を検証できる。仮想発火なら、その旨も保持する。
2. **見えている組で成立**：NEXT/NEXT2までの具体的な合法配置列で確認できる。
3. **条件付き仕込み**：必要色・セル・順番は分かるが、見えている組で成立を確認できない。
4. **根拠なし**：具体的な経路がない。

条件付き仕込みを完成済み回収として加点しない。未知の色を補った図は設計意図の説明にとどめる。
支持ぷよは未消去でも理由を記録する一方、物理的な「残り個数」から除外して成績を良く見せない。

## 5. 推薦の比較順

### 発火できる経路

合法・本線保持を確認した候補について、まず今の発火、次に早い先読み発火を優先する。
同じ発火時点では既存の別消し回避を維持し、その後に実発火後の残数を比較する。
発火を1手遅らせて残りを減らす候補には負けない。余りを別の単発消しで処分する加点もしない。

残数が同じなら従来の形状・操作性・決定的な配置順へ戻す。
比較条件と結果を骨格探索の終端、自由形の即時発火、最終候補ソートで共有する。
終端で構築中の用途点を足し直さない。

### 構築中の経路

第一段階は保守的に、**同じ骨格・同じ不足色と支持順・同じ完成段階**の候補同士で用途を比較する。
先読みで確認できた早い完成や安全な骨格進捗を、余剰回収の見込みで逆転させない。
これを単なる「補助点を100未満にする」だけで保証したとは扱わない。

- CURRENTの2個の用途と、既存ぷよが用途未確定／接続阻害へ変わる数を見る。
- 同程度のGTR進行なら、新しい用途未確定を増やさず、既存ぷよも活用できる候補を優先する。
- 頭・尾の仕込みは、必要色の競合、発火口、置ける順番、深い谷も比較する。
- 候補ごとに盤面全体の状態を再評価する。昔の減点を毎手累積し、同じぷよを何度も罰しない。
- 先読みで骨格を切り替える場合は、全ぷよの用途を新しい同一案で再計算する。
- 有用な代案がなければ、用途未確定の配置も残す。推薦不能や無理な伸ばしを作らない。

初手・折り返し未完成の選択は最初の採用範囲から外す。
尾完成後の効果と反例を確認してから、完成前への適用を別変更として検証する。
同じ進捗群だけの比較では効果が足りない場合も、無検証で範囲を広げない。

## 6. 実装単位の案

現行の[機能別モジュール＋レイヤード構成](../PROJECT-STRUCTURE.md)を維持する。

| 所有するファイル | 責務・変更案 |
|---|---|
| `advisor/ConstructionUse.ts`（新規案） | 1盤面・1骨格・1手順の用途と根拠を返す純粋な計算。既存の`PairPlacementUse`、頭・尾検証を利用し、物理シミュレーターを複製しない |
| `advisor/FireChoice.ts`（新規案） | 発火時点・別消し・実残数の比較規則を一元化。画面や測定処理から独立 |
| `advisor/FiveChainPlanner.ts` | 骨格ごとの用途評価を骨格選択前に適用。各経路の根拠を保持してビーム選別・最終比較を行う |
| `advisor/PlacementAdvisor.ts` | 自由形の発火比較と、最終候補の比較を共通規則へ揃える |
| `advisor/types.ts` | 推薦理由を任意の診断情報として保持。対象骨格、役割、根拠、必要色、評価範囲を明示 |
| `benchmark`／`scripts/analysis` | 余りの発生手・列・役割の推移、同盤面の別配置、失敗例を保存。本体から分析コードを呼ばない |
| `feedback`／`guide` | 確認済みの根拠から短い説明を出す。共有データの旧形式を壊さないよう、最初は任意項目で追加 |

推薦は同じ盤面と見えているツモから再現可能に保つ。長いゲーム履歴や乱数状態を入力にしない。
現在盤面のセルは呼び出し時の座標、先読みで追加するセルは手数と軸・子で識別する。
履歴上の「何手放置したか」は診断専用とし、今回の実行時評価には使わない。
消去・落下時は共通シミュレーターの元位置情報を使い、別経路の用途を混ぜない。

重い接続検証は既存の計算結果を再利用し、同じ盤面・骨格の集計を共有する。
キャッシュは盤面・対象骨格・頭の条件・必要な見えている組と評価版を区別し、上限を持つ。
盤面重複排除でも異なるCURRENTや経路の用途を合算しない。
全候補の詳しい説明生成は診断時に限定し、通常は選択に必要な集計だけを使う。

## 7. 実装する順序

1. **診断の固定**：用途と根拠を順位へ影響させず記録。今回の残数・発生手集計を再現できる分析をテスト化する。
2. **同じ手で発火する候補の改善**：39局面を回帰例にし、相方を本線で消せる発火配置を同点比較する。小さな改善であり、課題解決とは呼ばない。
3. **尾完成後の構築・待ちを改善**：CURRENTの2個だけでなく既存余剰も同じ案で評価する。既存の頭・雪崩・鶴亀を組み合わせるが、無条件の仮完成加点はしない。
4. **完成前の予防へ拡張**：1,004個・506個の発生局面を分類し、必要な範囲だけ適用する。一般的な多重や骨格種類追加は必要性を確認して別の変更とする。
5. **ガイド説明・共有を整える**：「土台に使う」「支持に使う」「あと何色で接続する」「用途未確定」を区別し、誤認定を利用者が報告できるようにする。

この順序は設計上の作業分割であり、外部タスクの作成・更新は行っていない。

## 8. 検証・採用基準の案

### 優先して守るもの

- 尾完成・本線5連鎖以上が各70%以上という最低条件だけでなく、同条件の現行版から完成数を落とさない。
- 既知の回帰集合では以前成功していたゲームの失敗化を確認する。獲得と喪失を相殺して総数だけで合格にしない。
- 今打てる本線を伸ばし目的で見逃さない。不正配置・ゲームオーバー・本線破壊・意図しない別消しを増やさない。
- 高い谷・ちぎり・発火までの手数の悪化を確認する。残数だけ改善しても自動採用しない。

### 改善の大きさ

段階2の限定改善と、構築全体の改善を区別する。
**構築改善の第一到達目安は平均残り5個以下、8個以上残るゲームを25%以下**とする案を置く。
利用者が指定した確定条件ではなく、現状7.72個・48.7%から有意義な改善を目指す開発目標案。
全局面0〜2個や、目標の実現可能性を保証しない。検証後に都合よく目標を下げて達成扱いにしない。

残りは本線発火全体と5連鎖成功だけの両方で表示し、前後とも発火した同じゲームで比較する。
平均・中央値・上位10%点・8個以上率・2個以下率・列別・発生段階別を保存する。
失敗ゲームを平均から外したことで良く見えないよう、失敗率と未発火盤面の用途未確定も併記する。
役割の認定率だけで改善を主張せず、実消去で参加した元ぷよ数・実残数を独立に照合する。

### 比較集合とテスト

- 現行v2を固定し、既知のseed 20260904／20260922の500件ずつを回帰に使用する。
  後者は今回のv2でまだ測定していないため、古い別版の結果をそのまま比較基準にしない。
- 別の未使用seedを履歴・gameSeedの重複確認後に予約し、候補固定後に500件を評価する。
  今回は予約・実行していない。同じ集合を再調整に使ったら未使用とは呼ばない。
- 色置換、軸子交換、支持は残るが必要な例、発火口を塞ぐ例、仮完成でだけ回収する例、
  同時の独立消し、頭と尾の色競合、骨格変更で用途が変わる例をテストする。
- 既存のY字優先・低い接続・発火点伸ばし・雪崩／鶴亀の回帰例を維持する。
- ライブ盤面と再現URLで推薦と説明が一致し、旧レポートの読み込みも維持することを確認する。
- 固定した代表局面で実行時間の中央値・上位5%点を前後測定する。暖機後・同じ環境で比較し、
  診断無効時の上位5%点が20%以上悪化する候補は、最適化または範囲縮小して再確認する。

## 9. この設計段階での結論

主対象は**尾完成後、組み終わりと発火を待つ間の配置**。
同時に、最後の発火配置の同点比較は小さく独立した修正として先に検証できる。
「余剰の減点を増やす」ではなく、「同じGTR進行で、2個と既存ぷよに具体的な用途を残す」を設計の中心にする。
この段階ではゲーム本体の変更、追加の自動対戦、採用済みという宣言は行わない。
